## 3. A 的讲解稿（可照读/按自己语气改写）

### 3.1 开场（约 40 秒）

> 老师好，我们是第 X 组，项目是「校园二手交易系统」。我负责总体架构、需求与 API 契约、跨模块协调和最终验收；B 负责前端，C 负责数据库，D 负责后端。今天我先介绍整体设计与协作方式，再现场演示主要功能，最后请组员补充各自模块。

### 3.2 项目背景与目标（约 1 分钟）

> 校园里二手物品交易信息分散在群聊和朋友圈，缺少一个集中的信息平台。我们的目标是做一个**功能闭环、分层清晰、四人可协作**的二手交易系统：注册登录后可以发布商品，所有人可以浏览、按名称搜索、按价格排序，普通用户只能管理自己发布的商品，管理员可以管理所有商品。
>
> 本期范围是课程要求内的核心闭环：注册/登录/登出、商品列表/搜索/排序/分页/详情、发布/修改/删除、角色权限。聊天、支付、图片上传、推荐等没有纳入本期，避免范围失控。

### 3.3 需求范围与角色权限（约 1.5 分钟）

> 系统有三类角色：
> 1. **游客**：浏览、搜索、排序、查看详情、注册登录；
> 2. **普通用户 USER**：发布商品，只能修改/删除自己的商品；
> 3. **管理员 ADMIN**：可以修改/删除所有商品。
>
> 权限不是靠前端隐藏按钮，而是**后端强制校验**：登录态保存在 HttpSession，拦截器负责认证，Service 在修改/删除前先查商品，再判断「管理员放行 → 本人放行 → 其他人 403」。商品归属只取 Session 里的当前用户 ID，请求里就算伪造 `userId` 也不会生效。

### 3.4 总体架构与技术选型（约 2 分钟）

> 架构是标准前后端分离：Vue 3 前端通过 `/api` 调用 Spring Boot 后端，后端分 Controller、Service、Mapper 三层，数据存 MySQL。前端开发期用 Vite 代理解决同源和 Cookie 问题，交付时把前端构建产物打进后端静态资源，单 Jar 同域运行，避免演示环境跨域。
>
> 技术选型遵循「够用、可解释」：
> - 后端 Spring Boot 3.3 + JDK 21；
> - 数据访问用 **MyBatis**，SQL 显式可控，方便数据库同学评审，也贴合课程教学；
> - 认证用 **HttpSession + Cookie**，单体应用实现简单、登出可立即失效；没有引入 JWT/Redis；
> - 密码用 **BCrypt**，数据库不存明文；
> - 前端 Vue 3 + Vite + Pinia + Element Plus，路由用 hash 模式，单 Jar 刷新不会 404。
>
> 我们有意没有引入 Redis、Docker、微服务、消息队列和完整的 Spring Security，因为课程项目规模不需要，引入反而增加讲解和维护成本。

### 3.5 数据库与 API 设计（约 2 分钟）

> 数据库两张表：`user` 和 `item`，一个用户对应多个商品。
> - `user`：id、username（唯一）、password_hash、role（USER/ADMIN）、时间字段；
> - `item`：id、item、item_price、contact_info、user_id（外键）、时间字段。
>
> `item_price` 用 `DECIMAL(10,2)` 避免浮点误差；用户名唯一且不区分大小写；外键使用 `RESTRICT`，用户本期不提供删除；商品是物理删除。索引包括用户名唯一键、`user_id`、`created_at`，价格排序索引视情况使用；`LIKE '%关键词%'` 前导通配符用不上普通索引，我们在课程数据量下接受全表扫描，C 同学做了 EXPLAIN 记录。
>
> API 统一以 `/api` 开头，统一返回 `{code, message, data}`，HTTP 状态和业务码成对使用；参数校验失败返回 400 + `fieldErrors`。浏览和搜索合并为一个 `GET /api/items`，因为资源、权限、响应结构相同，只是有没有 `keyword`，合并避免两套分页排序逻辑漂移。

### 3.6 现场演示串词（约 4～5 分钟）

> 下面现场演示。先看游客视角：打开列表，5 条测试商品；搜索「耳机」，按价格从低到高排序；点进详情，联系方式只在详情页展示。搜索/排序/分页状态会同步到 URL，刷新后仍保留。
>
> 然后登录普通用户 `student`：发布一件商品，填写名称、价格、联系方式，提交后进入详情；再进入编辑修改名称，保存；最后删除，二次确认后回到列表。可以看到普通用户只能看到自己商品的编辑/删除入口。
>
> 再看游客访问受保护页面：退出登录后直接打开发布页，会被路由守卫带回登录页；直接请求受保护接口则返回 401。
>
> 最后用管理员 `admin` 登录，打开 student 发布的商品，管理员同样能看到编辑/删除入口——后端对管理员放行。演示到这里，具体前端细节请 B 补充，数据库和 SQL 细节请 C 补充，后端接口实现请 D 补充。

### 3.7 团队协作、测试与质量（约 2 分钟）

> 协作上我们**契约先行**：先把需求、架构、API 契约、数据库设计、分工与流程写在 `docs/`，再并行开发。Git 使用功能分支 + PR + Merge Commit，禁止 Squash，保留每个人的独立提交记录；公共文件按归属修改，避免多人同时改同一个文件。
>
> 质量上：后端有 77 个自动化测试，覆盖 Service 业务分支、Controller 契约、拦截器和 Mapper XML；另外做了真实 MySQL 的接口 E2E（查询 13 项、写入 23 项）和浏览器 UI 验收（8 项）。数据库脚本可重复执行，种子数据固定为 2 账号 + 5 商品。
>
> 我们的原则是：**不把没跑过的测试说成通过**，验收记录都在 `docs/design-review.md`。

### 3.8 总结与不足（约 1 分钟）

> 总结一下：项目完成了课程要求的用户/权限模块、两张表、完整 CRUD、Git 分阶段提交和 README/SQL 文档，权限由后端强制，前后端字段与错误码统一。
>
> 不足也很明确：没有做 CSRF Token、HTTPS、登录限流和验证码；Session 存在内存，后端重启会丢登录态；商品是物理删除，不可恢复；搜索没有做全文索引；没有接 CI 和前端单元测试。这些是课程范围外的取舍，如果继续做，会按「安全 → 持久化 Session → 搜索索引 → CI」的顺序补。
>
> 我的讲解到这里，谢谢老师，欢迎提问。

1. **游客浏览**：确认 5 条商品；输入「耳机」→ 搜索 → 1 条；排序选「价格从低到高」；看页码/每页条数；点卡片进详情，指出联系方式只在详情出现。

## 6. 老师可能问的问题与参考答案

### A. 需求与范围

1. **为什么选这个题目？目标用户是谁？**
   面向校园学生的二手物品信息平台；学生有闲置物品要卖、也想低价买东西，群聊信息分散，平台提供集中浏览、搜索和发布。选题规模适中，能覆盖用户、权限、CRUD 和搜索排序等课程知识点。

2. **为什么不做支付、聊天、图片上传、推荐？**
   课程项目重点是完整闭环和分层设计，不是堆功能；支付/聊天涉及第三方、实时通信等额外复杂度，图片上传涉及文件存储与安全，推荐算法超出课程要求，所以明确列入「本期不做」，把范围控制住。

3. **游客能做什么？为什么允许游客浏览？**
   游客可以浏览列表、搜索、排序、看详情、注册和登录；不允许发布/修改/删除。允许游客浏览是二手信息平台的自然需求，也能降低使用门槛；写操作必须登录。

4. **管理员账号怎么创建？能通过注册接口创建管理员吗？**
   不能。注册接口固定写 `role=USER`；管理员只能由 `sql/data.sql` 种子或人工 SQL 设置。课程演示账号是 `admin/123456`。

5. **用户忘记密码怎么办？**
   本期未实现找回密码/验证码/邮件；如果要加，可以增加验证码校验接口 + 一次性重置 Token（存库并设过期时间）+ 重置密码页。课程范围内按「不做」处理。

6. **课程要求里的 MVC、两张表、CRUD、权限、Git 提交都满足了吗？**
   Controller/Service/Mapper 分层对应 MVC；`user` + `item` 两张表；商品完整增删改查；后端 Session + 角色 + 归属校验；Git 有 4 人分支、PR 和 Merge Commit 记录；README 和 SQL 脚本齐全。验收记录在 `design-review.md` §7.5。

### B. 架构与技术选型

7. **为什么采用前后端分离？**
   前端专注页面与交互，后端专注业务与权限，接口契约固定后可以并行开发；也符合课程要求的技术栈（Vue + Spring Boot）。代价是要处理跨域和联调，我们用 Vite 代理和统一 API 文档解决。

8. **为什么用 MyBatis 而不是 JPA？**
   MyBatis SQL 显式可控，数据库同学可以直接评审 SQL、优化查询与索引，动态搜索/排序在 XML 里更直观；课程数据模型简单，不需要 JPA 的复杂对象关系管理。

9. **为什么不用 Spring Security？**
   需求只有登录、角色和归属校验，自定义拦截器 + BCrypt 足够，代码量小、逻辑透明，便于答辩讲清楚；Spring Security 的过滤链对这个规模偏重。密码哈希复用了 `spring-security-crypto`。

10. **为什么用 Session 而不是 JWT？**
    单体应用、课程规模小；Session 服务端可立即失效，登出语义准确，前端不需要管理令牌。JWT 更适合无状态/分布式场景，但需要处理签名密钥、过期、刷新和登出黑名单，复杂度更高。

11. **为什么前端用 Vue 3 + Pinia + Element Plus + hash 路由？**
    Vue 3 组合式 API 适合小组协作；Pinia 是官方状态库，只管理登录用户；Element Plus 提供表单、表格、分页等组件；hash 路由在单 Jar 静态部署时刷新不会 404，不需要后端 SPA fallback。

12. **前后端怎么联调？跨域和 Cookie 怎么处理？**
    开发期前端 5173 通过 Vite 代理 `/api` 到 8080，浏览器视角同源，Cookie 自动携带；Axios 设置 `withCredentials: true`。交付时前端构建产物放进后端 `static/`，单 Jar 同域运行，彻底避免 CORS。

13. **为什么统一返回 `code/message/data`？成功为什么用 200 不用 201？**
    统一结构让前端拦截器只写一套成功/失败处理，业务码与 HTTP 状态成对；课程项目为了简化，创建/删除也都用 200 + `code=0`，契约里明确写死，前端只认 `code`。更严格的 REST 可以用 201/204，属于可选改进。

14. **为什么没有引入 Redis、Docker、微服务、CI？**
    课程规模和部署环境不需要：单机单 Jar + MySQL 足够演示；引入中间件会增加环境配置和讲解成本。CI 和缓存列入后续改进，不作为本期验收项。

### C. 权限与安全

15. **怎么防止普通用户修改/删除别人的商品？如果伪造 `userId` 呢？**
    修改/删除在 Service 中先按 id 查商品，再取 Session 里的当前用户：ADMIN 放行，否则 `item.user_id == currentUserId` 才放行，否则 403。请求体里的 `userId` 完全不参与判定，伪造也没有用；E2E 已验证伪造 `userId=999` 仍归属当前登录用户。

16. **401/403/404 怎么区分？404 先于 403 会不会泄露商品是否存在？**
    未登录 401，已登录但无权限 403，商品不存在 404。当前顺序是先查存在性再判权限，因此会暴露商品是否存在；这是课程规模下的取舍，如果产品要求隐藏，可以把 403 优先，但会改变契约和测试。

17. **密码怎么存？为什么用 BCrypt？**
    只存 BCrypt 哈希（cost 10），不存明文/可逆加密；BCrypt 自带随机盐、计算成本可调，能抵抗彩虹表和暴力破解。登录用 `matches` 校验，数据库和日志都不输出密码。

18. **SQL 注入怎么防？搜索和排序参数怎么处理？**
    MyBatis 全部使用 `#{}` 参数化，禁止 `${}` 拼接用户输入；搜索关键词先转义 `\`、`%`、`_` 再 `LIKE ... ESCAPE`；排序只接受 `price_asc`/`price_desc` 白名单，映射为固定 SQL 片段，不拼接用户输入。

19. **XSS 怎么防？**
    Vue 模板默认对插值做 HTML 转义，页面不使用 `v-html` 渲染用户内容；后端只返回 JSON，不返回 HTML。如果以后支持富文本，需要额外的白名单清洗。

20. **CSRF 做了吗？**
    本期没有加 CSRF Token，依赖 Cookie `HttpOnly` + `SameSite=Lax` + 开发期同源代理；这是课程范围内的取舍，生产环境会加 CSRF Token、HTTPS 和更严格的 CORS 配置。

21. **管理员权限是不是太大了？**
    课程需求就是管理员可管理所有商品；本期没有用户管理、封禁、角色修改等后台功能。生产环境会做审计日志、最小权限和二次确认。

22. **Session 存在哪里？后端重启登录失效怎么办？会话固定怎么防？**
    当前存在 Tomcat 内存，闲置 30 分钟过期，重启会丢失登录态，演示前避免重启；登录成功时先 `invalidate` 旧 Session 再创建新 Session，降低会话固定风险。生产可换 Spring Session + Redis。

23. **越权删除怎么验证的？有证据吗？**
    有：后端 E2E 用例中，普通用户修改/删除他人商品返回 403/10004 且数据不变；管理员操作成功；删除后详情返回 404。测试记录在 `design-review.md` §7.1/§7.5，代码在 `ItemServiceImplTest` 与 E2E 脚本中。

### D. 数据库

24. **两张表怎么设计？为什么两张表？**
    `user` 存账号、BCrypt 密码、角色；`item` 存商品名称、价格、联系方式、发布者 `user_id`（外键）。一个用户可以有多个商品，1:N 关系，两张表满足课程要求且不过度设计。

25. **价格为什么用 DECIMAL？用户名唯一和大小写怎么处理？**
    金额用 `DECIMAL(10,2)` 避免浮点误差，范围 `(0, 999999.99]`；`username` 有唯一键，排序规则 `utf8mb4_0900_ai_ci` 不区分大小写，`Admin` 和 `admin` 视为重复。

26. **索引怎么设计？LIKE 搜索为什么可能慢？EXPLAIN 结论是什么？**
    有 `uk_user_username`、`idx_item_user_id`、`idx_item_created_at`、`idx_item_price`。`LIKE '%关键词%'` 前导通配符无法做 B+Tree 范围定位，会全表扫描；课程数据量 ≤1 万可接受，没有引入全文索引/ES。C 的 EXPLAIN 记录在 `database-design.md` §6.1：默认排序和价格降序可利用索引，价格升序混合方向会 filesort，用户名查询走唯一索引。

27. **事务用在哪里？并发修改/删除怎么办？**
    写操作在 Service 层加 `@Transactional`；目前是单表写，数据库原子性即可。并发删除/修改时，UPDATE/DELETE 影响行数为 0 会归一为 404；注册并发重复用户名由数据库唯一键兜底为 409。

28. **删除是物理删除吗？数据能恢复吗？**
    商品是物理删除，不可恢复；用户本期不提供删除。课程规模选择简单方案；如果要保留记录，可改逻辑删除 `deleted` 字段并调整唯一键和查询条件。

29. **测试数据和管理员账号怎么初始化？**
    `sql/schema.sql` 建库建表（可重复执行），`sql/data.sql` 先删后插 2 个账号（admin/ADMIN、student/USER）和 5 条商品；密码是 `123456` 的 BCrypt 哈希，仅演示环境使用。重置方法见使用手册 §8。

### E. 接口与前端

30. **为什么浏览和搜索合并成一个接口？**
    同一资源、同一公开权限、同一响应结构，只是 `keyword` 是否为空；合并避免两套分页/排序逻辑和契约漂移。前端浏览就是不带 keyword，搜索就是带 keyword。

31. **分页/排序/搜索参数怎么校验？**
    `page ≥ 1`、`size ∈ [1,50]`、`keyword` trim 后 ≤50、`sort` 只允许 `price_asc`/`price_desc`；非法参数返回 400/10001 和 `fieldErrors`，前端也会做同样的表单/参数校验，但后端是最终防线。

32. **前端如何处理成功/失败和重复提交？**
    所有请求走 `utils/request.js`：HTTP 200 且 `code=0` 返回 `data`，否则统一抛出错误；401 清登录态跳登录，403/400/500 统一提示，400 的 `fieldErrors` 回填表单；提交按钮用 loading 状态防重复点击。

33. **列表卡片为什么不显示联系方式？接口为什么还返回？**
    列表只显示名称、价格、时间，减少联系方式公开暴露、页面更清爽；详情页再展示。接口的 `ItemVO` 列表和详情共用同一结构，返回 `contactInfo` 后端不用改，前端只是不渲染，属于展示约定。

34. **刷新后登录态怎么恢复？**
    Pinia 的 `user` store 在应用启动/路由守卫调用一次 `/api/auth/me`：成功恢复用户和角色，401 静默视为游客；后续请求由 Session Cookie 维持。

### F. 测试与协作

35. **怎么测试的？覆盖哪些？没覆盖什么？**
    后端 77 个测试：Service 业务分支、Controller MockMvc 契约（401/403/404/400/409、字段校验）、拦截器、Mapper XML 解析；真实 MySQL E2E：查询 13 项、写入 23 项；浏览器 UI 8 项。未覆盖：前端单元测试、自动化 CI、压力测试（只有 C 的 EXPLAIN 与 1 万行数据评估）。

36. **代码是谁写的？个人贡献怎么证明？A 做了什么？**
    A 负责需求、架构、API 契约、数据库设计审核、PR 评审、联调、验收、文档与交付；B 负责前端；C 负责数据库；D 负责后端业务。Git 有各成员的分支、提交和 PR 记录，Merge Commit 保留个人提交；A 没有承担业务编码，最后 3 处错误文案是经授权做的整合收尾，可如实说明。

37. **Git 怎么协作？为什么禁止 Squash？**
    功能分支 + PR 到 `main`，A 用 Merge Commit 合并；Squash 会把多次提交压成一个，丢失每位成员的独立提交记录，影响课程个人贡献度评分。冲突先 rebase，公共文件按归属人协调；分支保护没有强制启用，由 A 把关。

38. **开发中遇到过什么问题？怎么解决的？**
    主要是三类：开发期跨域/Cookie 用 Vite 代理 + `withCredentials` 解决；前后端字段命名用 camelCase ↔ snake_case 映射表统一；权限判定顺序和错误码用契约先行 + 测试固定。还有一次队友 PR 内容为空，A 复核发现后授权做了收尾修复并补测试。

39. **项目亮点是什么？**
    对课程项目来说，亮点是：契约先行（需求/架构/API/数据库文档齐全）、权限后端强制且可验证、统一响应与错误码、真实 E2E 与浏览器验收、四人分工与 Git 记录可追溯；不是靠堆技术，而是把范围控制住并做完整闭环。

40. **如果现在加图片上传/我的商品/用户管理，怎么做？**
    图片：`item` 加 `image_url` 或新增 `item_image` 表 + 上传接口（限制类型/大小、重命名存储）+ 前端上传组件；我的商品：列表接口加可选的 `userId` 过滤或新增 `/api/items/mine`；用户管理：管理员用户列表 + 禁用/角色修改接口，并补充权限与审计。都属于课程范围外扩展。

41. **如果用户量变大，性能上怎么改进？**
    先加合适的索引和分页上限，再考虑缓存热点列表、全文检索/搜索引擎、连接池与读写分离、前端懒加载；当前课程数据量不需要这些，属于后续演进。

42. **现场演示失败怎么办？**
    预案：用预构建 Jar + 重置数据库重启；浏览器保留截图和本文档；不要现场改代码。常见问题是 MySQL 未启动、8080/5173 端口占用、登录态不对，使用手册 §9 有排查清单。

43. **项目还有哪些不足？**
    没有 CSRF Token、HTTPS、登录限流/验证码；Session 在内存、重启丢失；物理删除不可恢复；搜索无全文索引；无 CI、无前端单测、无生产监控。这些都在设计评审中如实记录，没有包装成已完成。
